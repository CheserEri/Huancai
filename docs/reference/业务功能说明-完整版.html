第一部分 系统总览

1.1 产品定位与形态

面向课外培训机构（教培）的一体化经营管理系统。三端协同：

端 形态 使用者 主要职责
PC 管理端 Web（pro.legacy.cn/web） 校长、教务、财务、前台 全量业务操作与经营分析
教职工 App 「原系统」手机 App 教师、教务 记上课、点评、查课表
家长端 微信服务号「家长端」 家长 查课时、看点评、收通知、请假约课

配套硬件：磁卡考勤机、人脸识别考勤机。

1.2 账户与权限模型

机构（幻彩教育）
 └─ 校区（鲅鱼圈幻彩国学堂 / 新民幻彩国学堂）
     └─ 部门（教务部 / 财务部 …）
         └─ 员工（12 人）── 关联 ──> 角色 ──> 功能权限（能进哪些页面）
                                          └─> 数据权限（管辖哪些校区/部门的数据）
  • 当前 12 名员工中：机构主管 1 人、自定义权限 2 人、教务/教师若干
  • 角色示例：机构主管、教务、教师、财务、自定义权限
  • 权限是双层的：功能权限决定「能不能进这个菜单」，数据权限决定「进去后能看到哪些校区/部门的数据」。这也是本文 10 项 🔒 的成因。

1.3 业务主线

获客引流 → 咨询跟进 → 报名收费 → 分班排课 → 记上课扣课时 → 作业点评 → 续费/转退 → 经营报表
   ↑                                                              ↓
   └──────────────── 家长端触达（家长端）←────────────────────────┘

所有模块的数据最终汇入两个账户：学员课时账户（服务履约）和财务资金流水（钱）。

第四部分 平替方案业务分析

结论先行：不建议「全量 1:1 复刻」，建议「核心内核自建 + 外围能力对接 + 营销类功能砍掉」。
原系统 67 项二级功能里，真正决定业务能否运转的只有约 30 项；23 项升级空壳和多个零数据模块，自建收益极低。

4.1 平替的动机与真实边界

值得平替的理由

维度 说明
数据资产 学员、课时、财务是机构最核心的资产，长期沉淀在第三方，导出受限于「当前结果导出」而非全库
成本结构 按校区/学员规模订阅，叠加升级项（AI、直播、题库、电子合同）后年费会持续抬升
定制刚性 国学/语文类机构的特殊计费（赠送课时、活动抵扣、跨校区转课）在标准产品里只能变通
链路断裂 当前公众号模板消息未开通，家校推送形同虚设；自建可直接用小程序订阅消息重新设计
依赖风险 服务商调价、停服、政策变化（预收费监管）都会被动

必须正视的成本

项 说明
研发 核心 135 人日起，全量 290 人日；不含设计、测试、运维
迁移 课时余额按「学员×课程」迁移，是最容易出错的一步，需 1 个月双跑对账
运维 需要专人负责备份、故障、账号、微信资质
合规 未成年人个人信息、预收费资金监管、等保
迭代 原系统每年发版十几次，自建后这些都要自己扛

决策建议：先算一笔账——把原系统近 12 个月实际支付的总费用（含升级项）拉出来，对比「自研 TCO ÷ 3 年」。如果年费低于自研年化成本的 60%，且没有硬性定制需求，不建议全量自研；可先只自建「课时账户 + 财务」内核，其余继续用原系统。

4.4 核心业务规则（12 条硬骨头）

平替项目 80% 的坑都在这 12 条里，建议逐条写成测试用例。

R1 课时账户按「学员 × 课程」建立

同一学员报两门课，课时不能混用。账户带有效期，过期课时按机构规则处理（作废/延期/折算）。余额不允许直接 UPDATE，只能由流水汇总得出（或维护快照 + 增量）。

R2 四种收费模式的扣减规则不同

收费模式 计费口径 扣减规则 退费口径
按课时 总课时 × 单价 每记一次上课扣 N 课时 剩余课时 × 折后单价
按期 时间段内不限次 不扣课时，按到期日判断有效 按剩余天数比例
按次 次数包 每上课扣 1 次 剩余次数 × 单价
按期限次 时间段 + 次数上限 超出上限另行收费 双重判断，取低

R3 优惠必须分摊到订单行

订单级优惠（满减、折扣、优惠券、积分抵扣、活动立减）要按各订单行金额占比分摊。不分摊的话，退其中一门课时算不出「折后单价」，退费必然算错。这是历史订单里「学费优惠 500 元」这类字段的底层逻辑。

R4 退费公式

应退金额 = 该课程实收（含分摊优惠后） - 已消耗课时 × 折后单价 - 手续费
折后单价 = 该课程实收 ÷ 该课程总课时（含赠送课时则需约定是否计入分母）

必须明确三件事：①赠送课时是否计入分母；②已消耗课时按折后价还是原价计；③手续费规则。这三条不同，退费结果差异很大，也是家长纠纷高发点。

R5 转课

转出课程剩余金额 = 剩余课时 × 转出课程折后单价
转入课时数 = 转出课程剩余金额 ÷ 转入课程折后单价（向下取整，尾差进余额或补收）

跨校区转课还要处理收入归属：原校区冲减、新校区确认，否则两个校区的营收报表都会失真。

R6 排课四维冲突检测

教师、教室、班级、学员四个维度都不能时间重叠。约束建议用数据库唯一索引 + 应用层校验双保险：

UNIQUE(teacher_id, start_at) / UNIQUE(room_id, start_at) / UNIQUE(class_id, start_at)
学员冲突需查该班全部在读学员 + 试听学员

跨校区共享教师时，冲突检测必须跨校区，否则同一老师会被排到两个校区同一时段。

R7 考勤幂等 + 补记上课

同一课次重复签到、重复点「记上课」不能重复扣课时。用 (lesson_id, student_id) 作为幂等键，扣课流水写入前先查重。补记上课要能指定「哪一课次」，否则课时会串。

R8 确认收入（权责发生制）

家长交的学费是预收款（负债），随课时消耗逐次确认收入。财务上要能同时出三个口径：

口径 含义 用途
实收 当期收到的现金 现金流
应收 当期开单金额 业绩
确认收入 当期消耗课时对应的收入 真实经营利润

原系统的「确认收入列表」就是这个。从收付实现制切到权责发生制，会让报表数字大幅变化，切换前必须和历史口径对齐，否则老板会以为数据出错。

R9 欠费与上课权限

订单可挂账形成欠费。是否允许欠费学员继续上课是可配置开关。欠费学员在记上课、报名时应有明显提示。

R10 多校区数据隔离与汇总

  • 数据隔离：员工只能看管辖校区的数据（原系统的「管辖校区」字段）
  • 汇总：总部角色可跨校区合并
  • 跨校区学员：允许在 A 校区报名、B 校区上课，课时账户跟随学员而非校区

R11 学员状态机

潜在 → 试听 → 在读 → 停课 ⇄ 复课
                    ├→ 休学 → 复课
                    ├→ 退学（需结清退费）
                    └→ 结业（课时耗尽或课程结束）

状态影响：能否排课、能否扣课、是否计入在读人数、是否出现在待办。

R12 试听学员

试听不扣课时，但占用班级名额，且要计入教师课时工资的判定口径（历史排课里有「含试听学员」开关）。试听转正后要能把试听记录并入正式报读。

4.6 技术架构建议

层 选型 理由
PC 前端 Vue 3 + TypeScript + Element Plus 中后台表格/表单密集，Element Plus 生态成熟
家长端 微信小程序（原生或 Taro） 订阅消息能力只有小程序有，H5 做不到
后端 Spring Boot 3（或 NestJS） 单体优先，按域分模块（modular monolith），不要一开始上微服务
数据库 PostgreSQL numeric(12,2) 存金额，int 存课时（×100 存分/半课时）
缓存/锁 Redis 排课锁、幂等键、会话
消息 Redis Stream 或 RabbitMQ 推送、异步对账
文件 对象存储 + CDN 作业图片、点评图片
部署 云主机 + Docker Compose 1333 学员的体量，2C4G 起步足够

四个关键设计决策

  1. 金额用整数分存储，杜绝浮点误差；课时用整数（或 ×100 支持半课时）。
  2. 课时流水 append-only：任何余额变动都写一条流水，余额由流水汇总或定期快照，永不直接改余额字段。
  3. 所有资金/课时写操作带幂等键：(业务类型, 业务ID, 学员ID)，防重复提交与重复回调。
  4. 排课冲突用数据库唯一约束兜底：应用层校验会因并发漏判。

4.7 数据迁移方案

步骤 内容 注意
1 从原系统导出：学员花名册、报读列表、班级列表、课程、订单、财务流水、员工、课时余额 原系统导出是「当前结果」，需分页多次导出
2 课时余额必须按「学员 × 课程」导出，含剩余课时、有效期、赠送课时 只导总额无法续算，是最大坑
3 课程表从班级反推（因历史课程列表为 0） 需人工确认课程归一
4 试运行：新系统只读 + 双记账，老系统继续收费 至少 1 个月
5 五项对账：应收、实收、欠费、课时余额、预收款余额 差异必须归零再切换
6 切换：老系统只读封存，保留查询权限 建议保留 1 年

4.9 风险与合规

风险 说明 应对
课时余额迁移错账 家长剩余课时算错，直接引发投诉 迁移后逐学员对账，抽样 100% 人工复核高余额学员
财务口径切换 预收款/确认收入切换后报表不可比 新旧口径并行 3 个月，出对照表
微信触达受限 模板消息已受限，订阅消息需用户逐次授权 小程序订阅消息 + 短信兜底 + 服务号推文
未成年人信息 《个人信息保护法》对 14 岁以下有单独同意要求 监护人授权留痕、最小必要采集、脱敏展示
预收费监管 部分地区要求学费进监管账户、按课消划拨 对接银行存管，或保留「安心宝」类服务
电子合同效力 需 CA 证书与可信时间戳 不自研，直接对接 e签宝/法大大
发票 培训服务发票需与订单对应 对接百望/航信
等保与数据安全 学员信息属个人信息，需等级保护 至少等保二级，做好备份与权限审计
单点故障 小团队运维能力弱 每日备份 + 异地存储 + 故障预案
员工离职 账号未回收导致数据泄露 离职即禁用，操作日志留痕

4.10 成本测算口径（给公式，不编数字）

自研 3 年 TCO
  = 开发人日 × 人日成本
  + 云资源（服务器/存储/带宽）× 36
  + 第三方年费（短信/合同/直播/AI/发票）× 3
  + 运维人力（0.5~1 人）× 36
  + 每年迭代（P0 人日 × 20%）× 人日成本 × 3

原系统 3 年支出 = 年费（含升级项）× 3

盈亏平衡年限 = 自研 3 年 TCO ÷（原系统年费 - 自研年运维成本）

建议把原系统近 12 个月实际付款总额（含所有升级项、增值服务）作为分子基准，不要用官网报价。

4.11 需要决策的 8 个问题

  1. 是否必须保留多校区独立核算 + 合并报表？（决定财务模块复杂度，差异约 20 人日）
  2. 家长端能否接受从「公众号模板消息」改为「小程序订阅消息」？（触达率会下降，需短信兜底）
  3. 预收费是否需要资金监管账户？（涉及银行对接，可能让项目延期 1-2 个月）
  4. 现有 1333 学员的课时余额，能否从原系统导出到课程级？（不能的话要人工补录，工作量按学员数线性增长）
  5. 电子合同、发票、直播是否坚持不自研？（建议不自研）
  6. 排课是否需要跨校区教师共享？（决定冲突检测范围）
  7. 美团/抖音/小红书直连是否真的要用？（当前一个都没开通，建议砍掉）
  8. 谁负责上线后的日常运维与故障响应？（没人接就别自研）
